# Lenses

`schemas.lenses` lists the **lenses** an application has declared. A lens is a two-way projection
between a canonical record and a rendering of it: `get` turns the canonical into the rendering, and
`put` takes an edited rendering back to the canonical. Think of a song record and the timeline an
editor shows, or a timeline and the smaller plan a third-party service accepts.

The registry is for finding lenses, not for applying them. Nothing looks up "the lens for this
record" here and runs it. Code that applies a lens keeps calling it directly, and registering is
what makes the lens visible to everyone else.

## What gets registered

Each entry is a `LensRegistration`:

- **`key`** — a dotted `vendor.lens-name`, such as `audiostud.song-to-timeline`. It is an address in
  this registry, so it uses dots; a slash is not a legal key character.
- **`tier`** — whose truth the lens is, `HostApplied` or `EngineAuthoritative`. The tiers section
  below explains both.
- **`association`** — the lens itself (a `LensAssociation`: the canonical's `@id`, a locator, a
  direction, a claimed fidelity and the get/put pair), or a closure that builds it on first read.
- **`evidence`** — sample documents the round-trip laws are checked against.
- **`owner`** and **`of`** — the declaring package in `vendor/name` form, and a plain-words
  description for listings.

The key is not the association's `@id`. Two lenses can legitimately project the same canonical, and
keying by `@id` would make one silently replace the other. The `@id` keeps its slash
(`audiostud/timeline-otio`), because it is a schema identifier, not an address.

## Tiers: whose truth a lens is

Two applications can look at the same canonical record and render it differently, and both can be
right for their own purposes. The tier is how a lens says which kind of answer it is.

- **Host-applied** (`LensTier::HostApplied`) is one application's own mapping. That application
  declares it and applies it at its own call sites, and it is true only of that application's data.
  It is visible to everyone who reads the registry, but it is authoritative nowhere. If another
  application maps the same `@id` differently, the two are not in conflict, and neither one is the
  meaning of the record.
- **Engine-authoritative** (`LensTier::EngineAuthoritative`) is a projection the engine itself stands
  behind. It defines the mapping for every host, so a host that disagrees with it is wrong, not
  merely different.

**Registering is discoverability, not endorsement.** A lens joins the registry so that someone
searching for lens usage finds it. The tier keeps that visibility from reading as a blessing: a
host-applied lens listed beside an engine-authoritative one has not been promoted by being listed.

Two things are worth knowing today:

- **Nothing enforces anything by tier yet.** The tier is a recorded claim that readers can filter on
  with `ofTier()`. No code path refuses, prefers or overrides a lens because of its tier.
- **No engine-authoritative lens exists yet.** The live registrations are host-applied lenses
  declared by one application. The engine-authoritative tier is there so the first such binding has
  somewhere honest to go, without a host-applied lens being mistaken for it in the meantime.

Use `HostApplied` for a lens your own application declares. Reserve `EngineAuthoritative` for a
projection an engine package owns and stands behind for every host.

## Registering

Register from a provider's `boot()`. Pass the association and evidence as closures so nothing is
built until something actually reads the registry:

```php
use Schemastud\DataSchemas\Overlay\Lens\LensEvidence;
use Schemastud\DataSchemas\Overlay\Lens\LensRegistration;
use Schemastud\DataSchemas\Overlay\Lens\LensRegistry;
use Schemastud\DataSchemas\Overlay\Lens\LensTier;

$this->app->make(LensRegistry::class)->register(new LensRegistration(
    key: 'acme.order-to-invoice',
    tier: LensTier::HostApplied,
    association: fn () => OrderLenses::orderToInvoice(),
    evidence: new LensEvidence(fn () => [OrderLenses::sampleOrder()]),
    owner: 'acme/shop',
    of: 'Order → invoice document',
));
```

The [**duplicate-key policy**](/beam/docs/foundations/registries#key-policies) is **reject**: a
second registration under a taken key throws, naming the owner of the first. Two lenses over the
same record need two keys. A malformed key throws too, at the registration site, where it can be
fixed.

## Fidelity is proved, not claimed

An association declares a fidelity, either `LosslessEligible` or `Lossy`, but the registry never
repeats that claim. `certifiedFidelity($key)` runs the round-trip laws (GetPut and PutGet) against
the registration's evidence, and answers `Lossy` when the laws fail, when there is no evidence, or
when the key is unknown. An honest `Lossy` declaration needs no evidence at all.

## Reading it

- `all()` lists every registration in registration order.
- `get($key)` returns one, or null.
- `forId($id)` returns *every* lens over one canonical `@id`, rather than choosing one for you.
- `ofTier(LensTier::EngineAuthoritative)` filters by tier.
- `describe()` returns flat rows with each lens's tier and certified fidelity, for a listing.
